# tengu-flags design

This file is the maintained design of record for the site and its data: a reader holding it alone can build a row, a page or a pipeline stage that fits the others. It is written for a model that will implement or extend the project; the page itself and the README are written for people and follow their own register. A change to a rule here is written into the passage that owns it, never appended as a note.

## What the site is

`tengu://flags` is a static page in the shape of `chrome://flags` for one Claude Code version at a time. ONE table, a search box at the top (FlexSearch over every visible field), one row per entry, `#<slug>` in the URL scrolling to and highlighting a row, the selected switches encoded in the URL so a link reproduces them, and an export of the selection as the `env` block of a `settings.json` file plus the settings keys that have no env form. A version picker switches the whole table; a row that exists in one version and not another says so.

The page promises only what the binary honours. Every row names where it was read (the Claude Code version and a byte offset: the read site itself on a gate or env row, the start of the reading that holds the site on a change row), and a toggle appears only on a row whose switch the client reads in normal use. A row with no such switch is still in the table, greyed, so a person who searches for it finds it and reads why it cannot be flipped and what, if anything, stands in for a switch.

## The three kinds of row, one table

| kind | what it stands for | has a toggle | source of the row |
|---|---|---|---|
| `gate` | a `tengu_*` feature gate the client reads through the GrowthBook reader API | yes, when the gate has an inline env or settings override; no otherwise (greyed, with the reason) | the gate pipeline over one build |
| `env` | an environment variable the client reads through its typed registry or a direct `process.env` read | yes (the variable itself is the switch); greyed when the variable describes the host rather than a choice | the env pipeline over one build |
| `change` | a behaviour that moved between versions with no runtime switch: a tool or command removed or added, a gate graduated into a constant, a default changed | no; the row carries the version it entered, the mechanism, and the workarounds, or says there is none and since when | the change pipeline over the version ladder |

Telemetry event names (`tengu_*` strings passed to the event logger) are not rows. They are counted per version in `index.json` and listed in the evidence files, because a reader who meets one in a transcript should be able to learn it is an event and not a switch; the search box finds them in that listing through a visible "telemetry events" filter that is off by default.

## Row schemas

Every row carries `slug` (lowercase, `[a-z0-9-]`, unique across kinds and versions: a gate's slug is its identifier with `tengu_` removed and `_` turned to `-`; an env row's is the variable lowercased with `_` turned to `-`; a change row's is a short noun phrase), `kind`, `name` (the identifier, variable or title as the binary spells it), `what` (one or two short sentences a person reads, each under 160 characters and never two facts joined by a comma: what the row controls or what changed; an `inferred` sentence says in its own words that it rests on the name, varying from row to row, and a sentence that could say nothing beyond "a switch" is `null` instead), `whatBasis` (`read` when the branch was read and the sentence says what the code at the site does, `inferred` when the sentence rests on the name and nearby strings, `null` when no sentence was written; a sentence names no step of the catalogue's own process, because the basis field carries that), and `provenance` (an array of `{version, offset}`, an entry optionally carrying `role`: `read` for a read site, `binding` for an occurrence that is not a read site: the identifier's own declaration when no read site names it, or the construction that decides what every read of it returns (the rows read only through an empty registry all cite the one line that builds that registry); and optionally `platform`, when the read was taken in a build other than darwin-arm64, as `win32-x64`). `version` is a release triple and, with no `platform`, names the darwin-arm64 build of that release. An offset is the whole of the evidence a row carries about the binary: a reader who holds that build finds the site by the number, and the repository quotes nothing from it (the section "What is published about the binary"). On a gate or env row the offset is the read site itself; on a change row it is where the change pipeline's reading of the site began, and the site sits within the 700 characters that follow it, which is what `changes.receipts.md` states and a reader of a change row allows for.

## What is published about the binary

The client's code is not published here, in any length, in any file: no excerpt of its JavaScript in the data, the evidence, the receipts, a commit message, a test fixture or the page. What is published about a build is the offset of a site, a count, the name of an identifier, a gate, a variable, a tool, a command or a setting as the build spells it, a string the client shows to a model or to a person (a prompt sentence, a tool description, a UI line, an error message), and an explanation of what the code at a site does, in the project's own words, as prose or as a Mermaid flowchart. A minified identifier the build invented is code and is named by its offset ("the factory at 162875978"), never by its letters. The validator refuses a string in the data or a line of the receipts that reads as code (the operator-shaped runs a minifier leaves: a keyword glued to a semicolon or a brace, a block that opens straight onto a statement, an arrow function, the minifier's spellings of true, false and undefined, an optional chain, a strict comparison, a logical operator glued to its operands; `tools/lib/codeshape.ts` holds each pattern beside its reason, and its unit test proves each on a refused and an accepted specimen), so the rule holds mechanically on every commit. A gate effect's `text`, `summary`, `where` and `mermaid` and the row's `values` are strings like any other and pass that rule. A flow effect's `mermaid` string also passes the flowchart rule of `tools/lib/mermaid.ts`: it opens with `flowchart` or `graph`; no label (the text in a node bracket, between a link's pipes or in quotes) carries a name glued to an opening parenthesis, which is a call (`Ce(`), where prose spaces a parenthesis from its word; and no node id beside a link or a bracket is a token shaped like a minifier's name, one to three characters carrying `$`, `_`, a digit or both cases, or a lone lowercase letter. A capital letter with optional digits (`A`, `B2`) is Mermaid's own id convention and passes, and so does a short lowercase word, because no rule on the letters alone tells `ce` from `ok`. The project's own source code under `src/`, `tools/` and `tests/` is outside the rule, which governs what is published about the binary. A build downloaded for a read stays in the operator's cache outside the repository.

A `gate` row adds `classes` (`["gate"]`, or with `"config-key"` or `"event"` when the identifier also occurs that way), `default` (the second argument at the read site as a JSON value, where `null` is the literal `null` the site passes; the literal a declared value holds when that literal sits in the same module; `{"expr": "<what the argument is, in words>"}` when it is not a literal, such as a value declared elsewhere in the build, the result of a call or `undefined`, because the expression itself is the client's code; `{"unknown": "<reason>"}` when no default could be read, as for a gate read from client data alone), `valueSource` (a subset of `growthbook`, `clientdata`, `config`), `cacheReach` (`full`, `partial`, `none`, `direct`: what the frozen-disk mode reaches, see below), `override` (`null`, or an array of `{"shape": "env"|"settings", "key": "<VAR or settings key>", "direction": "both"|"on"|"off", "note"?: "<what the override replaces, when it is not the whole value>"}`, an array even when it holds one entry; an entry whose key names an `inert` env row is not an override and is left off), `prerequisites` (an array of `{"kind": "env"|"flag"|"settings", "key": "<name>", "note": "<why the gate needs it>"}`: the variables, flags or settings that must be set for the gate to matter), `effects` (what the gate changes, as an array of effect objects a person reads under the `what` sentence; each is a closed object and carries `kind` and `when`, the gate state or value that produces it: `"on"` or `"off"` for the two states of a boolean gate, otherwise one lowercase value word naming the served value (`[a-z0-9][a-z0-9._-]*`, at most 40 characters, such as `"cohort"`, `"3"` or `"0.5"`), never a phrase, because a condition that needs words belongs in `where`, `summary` or `values`, and never `"true"` or `"false"`, so a boolean state has one spelling: a `prompt` effect carries `where` (which prompt, tool description or system-prompt section, in words) and `text` (the sentence or passage the gate inserts, removes or replaces, VERBATIM, because a reader who meets it in a transcript must be able to search this page for it); a `flow` effect carries `where` (the operation, in words), `summary` (one sentence) and `mermaid` (a flowchart of the branch the gate decides, in the project's own node labels, no identifier from the build); a `value` effect carries `name` (what the number or string parameterises) and `unit` where one applies, the key absent where none does; a `ui` effect carries `text` (the verbatim line the person sees) and `where`; a `telemetry` effect carries `summary` for a gate that changes only what is logged; an empty array is a row whose effects have not been read yet, and it says nothing about `whatBasis`, which describes the `what` sentence alone: a row can state what it controls from a read site and still wait for its effects), `values` (`null`, or one sentence saying how the served value, the model's own configuration and the override compose when the gate is not a plain boolean, such as a three-way forced / none / cohort decision), and `floor` (`{"build": "<version>", "previousRung": "<version>|null", "basis": "literal"}`; a literal floor dates the identifier, never the behaviour).

An `env` row adds `type` (the registry's parser: `bool`, `triBool`, `int`, `str` for both the trimmed and the raw string parsers, `{"enum": [<values>]}`, `direct` for a bare `process.env` read, or `null` on an inert row whose name reaches no parser), `documented` (the URL of the documentation page that lists the variable, `false` when the fetched documentation does not list it, `"unknown"` when the documentation could not be read), `overrides` (an array of `{"gate": "<gate slug>", "direction": "both"|"on"|"off"}`, empty when the variable overrides no gate row), `hostContext` (`true` when the variable describes the running environment rather than a user choice, which greys the row), `inert` (`null`, or one or two short sentences saying why setting the variable changes nothing in this build: it is declared in the registry and read by no code, it is read only through a registry built over an empty shape so every read yields undefined, or its read site's branch has no effect; one wording stands for one reason across the file; an inert row is greyed like a hostContext one and carries `hostContext` false, so a grey row has one reason; "read by no code" is decided over every occurrence of the name as a quoted string in the build and not over the registry's getters alone, because a by-name lookup, a direct property read and a plugin's `env.get` all bypass the getters, and a row such a read reaches is a `read` row whose provenance cites the read site), and `floor` as above. Two variables whose names differ only in case fold into one row named by the upper-case spelling, because the slug rule cannot tell them apart. A variable whose every read is a gate's override site is not an env row at all: it is that gate's switch, the gate row's `override` entry carries it, the gate's search document indexes its name, and the page shows one row for one switch, because a reader who searches the variable must land on the gate it flips and not on a second row that repeats the gate in other words. An env row exists for a variable the client reads on its own account.

A `change` row adds `surface` (`tool`, `command`, `hook-event`, `settings-key`, `env`, `gate`, `default`), `direction` (`removed`, `added`, `renamed`, `graduated`, `default-changed`), `enteredAt` (`{"version": "<first version with the new behaviour>", "lowerBound": "<last version with the old one>", "method": "bisect"|"cached-rung"|"changelog"}`; under `cached-rung` the two bounds are the cached rungs either side; under `bisect` they are the two builds the bisect ended between; under `changelog` the version is the CHANGELOG heading that names the change and the lower bound is the release before it in the version universe, a reading of the list and not of bytes), `mechanism` (one or two sentences saying in words what the code that decides it does, before and after, each site named by its offset), `workarounds` (an array of `{"kind": "flag"|"env"|"entrypoint"|"settings"|"none", "text": "<what to do>"}`; `none` is a real entry and carries `since`, the version from which there has been no way round, read as `enteredAt.version` when absent), and `changelog` (`{"version": "<heading>", "quote": "<the line>"}` when the official CHANGELOG names it, else `null`). A change row's `provenance` names the side where the name occurs, because an absence has no site to point at; a hook-event or settings-key row also cites the other side's event array or schema object as a read.

## Files

```
index.html, src/   the page: TypeScript 7 and SolidJS 2 components under src/, styled with Tailwind CSS 4 utility classes, built by Vite 8;
                   src/schema/ holds the Zod 4 schemas of every row kind and file below, the ONE statement of the shapes this file
                   describes, parsed by the validator and by the page at load (a data file that fails to parse is reported, never
                   half-rendered); FlexSearch comes from its npm package, no vendored copy
sample/            a labelled made-up data tree the page opens under ?dev=sample while developing, left out of dist/;
                   the build writes it no search corpus, so the page builds one in the browser
data/index.json    {"versions": [{"version", "sha256", "readAt", "counts": {"gates", "env", "changes", "events"}}]}, ascending by
                   version; `changes` counts the rows whose enteredAt.version is that version; no timestamp, so a rerun reproduces the bytes
data/versions/<version>/meta.json     {"version", "sha256", "readAt": "<the BUILD_TIME value of the build's manifest, when known>"}
data/versions/<version>/gates.json    [gate rows]
data/versions/<version>/env.json      [env rows]
data/versions/<version>/events.json   ["tengu_...", ...]  the telemetry event names, sorted
data/changes.json                     every change row, across versions
data/evidence/<version>/gates.receipts.md      the counting rules and totals behind that version's gate and event rows
data/evidence/<version>/env.receipts.md        the same, for the env rows
data/evidence/changes.receipts.md              the surfaces diffed, the candidates, the changelog hits and every bisect step
tools/validate.ts    parses every file above through src/schema/ and refuses any string or receipts line that reads as code (exit 1 on
                     the first violation, naming the file, the row and the field)
tools/index.ts       writes data/index.json from whatever the three pipelines have written
tools/build-data.ts  writes dist/search/<version>.json, the per-version document corpus (one document per gate, env and change row
                     and per telemetry event) from which the page builds its search index in the browser, and copies data/ into
                     dist/data/; the Vite build writes the page beside them; neither step edits data/
tests/               vitest unit tests over the pure functions (the search documents, the per-version change selection, the slug and
                     URL rules) and Playwright checks that open the built dist/ on the real data files and assert the counts, the
                     toggle and grey-row split, the #slug jump, the export block and a search hit, and that serve the
                     sample tree to it to open a specimen gate's effects
biome.jsonc, tsconfig.json, tsconfig.node.json, vite.config.ts, playwright.config.ts, package.json, .husky/, tools/gate/

.github/workflows/pages.yml   on push to main: npm ci, the same gate the hook runs, the build, the Playwright checks against it, publish dist/ to gh-pages
```

One pipeline owns each file: the gate pipeline writes `gates.json`, `events.json`, `meta.json` and the `gates.*` evidence; the env pipeline writes `env.json` and the `env.*` evidence; the change pipeline writes `changes.json` and the `changes.*` evidence; `index.json` is regenerated by `tools/index.ts` from whatever the three have written, so no two pipelines touch one file. `main` holds the source, the data and the evidence; `gh-pages` holds `dist/` and nothing else, written only by the workflow. There is no server; the build needs Node 22.12 or newer (the floor of the Solid 2 packages, their Vite plugin and Vitest 5) and the packages `package.json` pins. The extraction scripts that produce `data/` from a Claude Code binary are kept outside this repository; `receipts.md` states each counting rule so a reader can reproduce a number with the tools named there.

## Toolchain and gates

The code is TypeScript 7 throughout (the page, the tools, the tests), the page is SolidJS 2 with Tailwind CSS 4, the shapes are Zod 4 schemas, the bundler is Vite 8, and Biome is the formatter and linter. Every version is pinned exactly in `package.json`; SolidJS 2 is pinned at a release candidate because its component API is the one the page is written against, and the pin moves when 2.0 ships. The reason for one strict toolchain is the reader of this code: a model extends it, and a model acts on what the types and the linter make explicit and silently guesses at what they leave implicit.

The gates are the ones csift carries, applied to TypeScript, and they run as one command, `npm run gate`, from the pre-commit hook (husky) and from the Pages workflow alike, so a commit that passes locally is the commit CI builds:

- The structure gate: at most 600 lines per source file, 20 source files per folder, 16 subfolders per folder, 5 folder levels below `src/`, `tools/` and `tests/`; generated files and `node_modules/` are outside it. A cap that binds is a reason to re-manage the layout, never to raise the cap or squeeze a file.
- Biome, formatter and linter, with no warning allowed: the recommended set plus the function cognitive-complexity ceiling of 25 (csift's), `any` refused everywhere (the boundary parses `unknown` through a schema), unused variables, imports and parameters refused unless the name opens with `_`, an unused expression refused, a promise left floating refused, a non-null assertion refused, `@ts-ignore` refused in favour of `@ts-expect-error`. Where Biome's installed catalogue has no rule for one of these intents, the gate names the compiler flag or the check that carries it instead, and `biome.jsonc` states beside every non-default rule which intent it carries.
- The TypeScript check, run by the native `tsc` binary the TypeScript 7 package ships, under `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `verbatimModuleSyntax` and `isolatedModules`.
- The unit tests, then the data validator over `data/`.
- The suppression check: a lint or type suppression is allowed only with its reason in the comment, `// biome-ignore lint/<group>/<rule>: <why this line is right>` and `// @ts-expect-error <why>`; a suppression with no reason, and any `@ts-ignore` or `eslint-disable`, fails the gate.

The Playwright checks need a built page and a browser, so they run in the Pages workflow and from the pre-push hook, not on every commit.

## How a gate's value is decided (the mechanism behind every gate row)

The client asks GrowthBook for its gates at startup through a remote-eval POST to the Anthropic API, with a first-fetch timeout of five seconds and a refresh every 360 minutes by default. The served map is written by one writer into the global config file (`~/.claude.json`, or the file under `CLAUDE_CONFIG_DIR`) under `cachedGrowthBookFeatures`, replacing the whole map on every write. A read answers in this order: an environment or config override hook, the served payload, the read site's default when a payload exists but lacks the key, the disk cache, the default. In the shipped build both generic override hooks are stubs that return nothing, so the only overrides that exist are the ones written inline beside a gate's read site: an environment variable read from the typed env registry (`VAR ?? read(gate, default)` replaces the value in both directions; `VAR || read(...)` forces on; `if (VAR) return false` forces off) or a settings key. That registry is five objects, not one: the main one is assembled from eight shape parts (1,088 keys at 2.1.287, the 298-getter part among them), two small ones hold two keys and one key, and two are built over empty shapes, so a variable read only through those two always reads undefined and an override written against it does nothing, which is what the env row's `inert` field records. A settings file's `env` block is copied into the process environment at startup, so an env override can be set from `settings.json` as well as from the shell. A second remote source, "client data" fetched at bootstrap, carries a few gate-like keys of its own.

The frozen-disk mode is the one path that reaches nearly every gate: with telemetry off and `CLAUDE_CODE_GB_DISK_CACHE_WHEN_TELEMETRY_OFF` set, no GrowthBook client is created, nothing is fetched or rewritten, and every value reader answers from the editable cache. Its cost is telemetry off and no refresh, and gates read through the blocking readers or client data do not follow it. The page states it once, as an advanced note, and puts no toggle on it.

## How a change is dated (the method behind every change row)

Dating is never a per-version read of the whole ladder. The surfaces that can be enumerated mechanically (the tool registry's names, the slash-command registry, the hook event names, the settings schema keys, the env registry names, the `tengu_*` set) are extracted from every cached build and diffed between neighbouring rungs; each difference is a candidate change with a gap. The official CHANGELOG (fetched once and kept beside the pipeline) is searched for the candidate's words to narrow the gap to a version or a few. Only then is a bisect run: the midpoint build of the remaining gap is downloaded from the release bucket, verified against its manifest, read for the surface, and the gap halved, so a candidate costs about log2(gap) downloads and candidates sharing a gap share the downloads. Every downloaded build joins the cache so no version is fetched twice. The row records the method that dated it and both bounds. The version universe the bounds are drawn from is the union of the installer's version list, the CHANGELOG's headings and the cached ladder, because each list lacks versions the others carry. The slash-command surface includes the bundled skills' `userInvocable` registrations beside the built-in command objects, or a command that moved into a bundled skill reads as removed. The two oldest cached builds (1.0.60 and 2.0.0) use an older Bun module table that the module-graph reader does not parse, so an extractor reads module text only and never the whole file, which would put the runtime's own strings into a surface.

## The page's behaviour

- The version picker lists `index.json`'s versions; the newest is selected by default; `?v=<version>` pins one.
- The table shows gate and env rows with a toggle where the row has one, change rows greyed, and telemetry events only when the filter is on. A greyed row's description says why there is no switch and lists the workarounds.
- The search box matches `name`, `slug`, `what`, the override key, the workaround text, and a gate's effects (each effect's `where`, verbatim `text` and `summary`) and its `values` sentence, so a sentence met in a transcript finds the gate that put it there; a `#<slug>` fragment scrolls to the row and highlights it.
- A toggle sets a value: for a `both` override the two states; for `on` and `off` one state. The selection is encoded in the URL as `?c=<base64url of a compact JSON object {slug: value}>` and decoded on load.
- Export renders two blocks a person can paste: the `env` object for `settings.json` (every env-shaped switch with its value) and a list of settings keys with their values; it names the version the values were read against.
- The row's detail opens inline, under the `what` sentence: the effects, the `values` sentence, and the provenance as the build and the offset. A prompt or UI effect shows `where` and `when` and its verbatim `text` in a quoted block; a flow effect shows `where`, `when` and its `summary`, and the Mermaid diagram drawn in the browser from the row's own text the first time the detail opens; a value effect shows `name`, `unit` and `when`; a telemetry effect shows its `summary` and `when`. The renderer is the `mermaid` npm package, pinned exactly in `package.json` and loaded by a dynamic import the first time a detail holding a flowchart opens, so a reader who opens none never downloads it; it runs with its strict security level, which draws labels as text and binds no click. A row with no effects and no `values` sentence opens onto the provenance alone. Nothing is fetched beyond the data files and the page's own code, and nothing from the binary is shown.
- The page runs from any static host (GitHub Pages, `python3 -m http.server -d dist`) and not from `file://`, where the browser refuses the module script and the data fetches without a launch flag; when `index.json` fails to load, or a data file fails its schema, the page says so and renders no row.

## What is owed before the page is public

- Every `what`, `inert` and workaround sentence shown on the page is person-read text written under the human-writing register, read once by a non-author against the bytes at the row's own offsets and against the extraction draft, and corrected where the draft misread the bytes; a pipeline that adds rows hands its drafts through the same two steps before they reach the page. The extraction drafts the pipelines write are not the page's text, and the rate the cold read measured on the gate drafts (about three sentences in a hundred wrong against the bytes they describe) is why the read is against the bytes and never against the draft alone.
- The repository's commits and files follow the privacy rules of the operator's other public repository: no machine-local path, no session identifier, no person's name, no credential, the identity and signing posture the same. The check for the operator's scratch directory matches its path forms and not the bare word, because the slug of the real variable `CLAUDE_TMPDIR` contains that word.
- A row is published only with its provenance; a row without an offset is not a row.
- A row whose switch does nothing in the build it was read from carries `inert` and no toggle: the variables declared and never read, the variables read only through the empty registries, and the read sites whose branch has no effect are greyed before the page is public, and the gate overrides keyed on them are removed from the gate rows.
